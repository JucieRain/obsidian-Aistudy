# 组织级AI转型

> AI工程化转型是一把手工程，不是大家自发干；是生死战，不是选择题；是组织级系统变革，不是研发内工具升级。

## 核心定义

组织级AI软件工程转型，指用 AI Agent 重构软件生产的全链路——需求如何表达、架构如何决策、代码如何生成、测试如何验证、团队如何协作。

## 为什么必须是一把手工程？

触及三个深层矛盾：

| 矛盾类型 | 说明 |
|---------|------|
| **利益边界** | AI介入后，原有岗位的权力结构会被打乱 |
| **流程惯性** | 手工写设计文档、逐行code review等习惯根深蒂固 |
| **短期KPI vs 长期能力** | 烧token是即时成本，能力沉淀是滞后的 |

## 烧token的本质

**烧token越多，脑子里幻觉越少**

AI在软件工程中的不可靠，根源在于缺乏真实工程约束下的充分试错。当它被嵌入完整工程闭环——依赖图谱、历史bug关联、CI/CD反馈、运行时监控——每一次失败都是一次约束的注入。

烧token的真正价值：
- 处理过依赖冲突自动修复 → 学会检查版本兼容性
- 处理过跨服务接口变更级联更新 → 学会"这个改动会影响谁"
- 处理过历史bug关联 → 学会"这个重构不值得做"

## 全员覆盖

**中层主管和技术骨干必须亲自烧token**

不能形成"精英小分队"，因为中层主管和技术骨干是转型的"腰"，腰断了先锋再怎么冲都没用。

| 死角类型 | 表现 | 后果 |
|---------|------|------|
| 中层主管 | 嘴上支持，自己不动手 | 团队只敢做"AI辅助"级别动作 |
| 技术骨干 | 觉得自己比AI快，不屑学习 | 核心模块无法被工程化 |
| HR/质量/运维 | 认为AI只是开发的事 | 组织分裂，流程断裂 |
| 产品/需求侧 | 继续写模糊需求文档 | Agent无法获取可执行规约 |

## 从烧token到系统级治理

当各业务团队烧token有了真实体感后，会主动识别"哪些业务可以用AI软件工程替换"，提出系统级问题：
- 现有代码仓分支策略是否支持agent并行开发？
- CI/CD流水线能否承载每小时数十次agent提交？
- 测试环境能否动态按需创建？
- 需求管理工具能否导出机器可读的spec？

## 必须早定早解的问题

| 问题 | 核心矛盾 | 建议方向 |
|-----|---------|---------|
| 统一agent.md | 个体自由 vs 组织规范 | 统一基础框架，留20%扩展字段 |
| 选SDD框架 | 工具锁定 vs 效率提升 | 选OpenSpec声明式、可diff的 |
| story spec删不删 | 历史债 vs 可追溯 | 合并到.spec/目录随代码版本管理 |
| skill分级体系 | 复用性 vs 维护成本 | L0通用、L1框架级、L2业务级 |
| code review agent化 | 自动化 vs 关键判断 | 规则类全自动，架构类生成review问题 |
| 小型化战阵型 | 沟通成本 vs 规模效率 | 不超过5人的小组是AI工程时代最佳实践 |

## 立即可启动的行动清单

1. **虚假繁荣扫描**：检查过去一个月PR，AI跨模块重构占比低于30%说明在假装转型
2. **设立烧token实验基金**：每人每月50-100美元等值token，每周五展示实验结果
3. **选最痛项目做全流程改造**：从需求spec到部署yaml，记录所有卡点
