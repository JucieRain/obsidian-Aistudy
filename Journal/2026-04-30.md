## 二、知识库管理（TSE 测试工作集）

### 2.1 需求痛点

- **核心痛点**：约 100 份历史文档处于混乱状态，格式不统一（文档 + Excel），无结构化管理
- **当前聚焦**：文档格式转换问题（优先解决）
- **紧急痛点**：当前几个测试用例输出的格式转换需求
- Markdown ↔ Word 转换存在格式失真问题
- 组网图无法在 Markdown 中直接呈现，也无法从 Word 还原
- 测试用例、测试数据、测试指导三者缺乏关联（后续处理）

### 2.2 关键要做的事情

| 关键事项 | 说明 | 关键点 |
|---------|------|-------|
| **格式转换方案** | Markdown ↔ Word 转换方案研究 | 🔴 当前优先，解决测试用例输出痛点 |
| **测试用例输出** | 解决当前几个测试用例的格式转换 | 紧急需求，验证方案可行性 |
| **底层架构选型** | 确定知识库承载方案 | 架构讨论预计很快出结果 |
| **文件结构设计** | 定义工作区目录结构 + AI 引导说明 | 基于分类维度：运营商 / 年份 / 项目 |
| **用例模板制定** | 制定 Markdown 格式 + 双向链接规范 | 模板确定后才能批量迁移 |
| **组网图方案** | 寻找通用标准格式，内外网通用 | 需调研 Mermaid / Draw.io / 其他方案 |

### 2.3 约束与输入

| 约束项 | 内容 |
|-------|------|
| 当前优先级 | 格式转换 > 整体知识库管理架构 |
| 紧急需求 | 当前几个测试用例输出的格式转换 |
| 底层架构倾向 | Obsidian 承载，架构讨论预计很快出结果 |
| 组网图现状 | PPT 形状 / 公司内 Visio 类软件 |
| 组网图目标 | 通用标准形式，内外网通用 |
| 历史文档分类维度 | 运营商 → 年份 → 项目 |
| 单项目内容结构 | 最终版规范 + 过程稿 + 数据结果（预测 + 测试） + 组网/配置条件 |
| 存档范围 | 尚未完全确定，需用户自行梳理 |
| 公司系统 | 有系统但无法精细化管理 |

### 2.4 五一任务清单

- [ ] 格式转换方案研究（调研 + 实验）← 当前优先
- [ ] 测试用例输出格式转换（执行）← 紧急需求
- [ ] Obsidian 架构调研（调研，2-3h）→ 交付物：调研结论（是否可行 + 参考案例）
- [ ] 文件结构设计（设计，2h）→ 交付物：目录结构方案
- [ ] 用例 Markdown 模板制定（设计，2h）→ 交付物：模板文件
- [ ] 组网图方案调研（调研，2h）→ 交付物：方案建议（Mermaid / Draw.io / 其他）
- [ ] 用例 Markdown 化试点（执行，3h）→ 交付物：5-10 份试点文档

### 2.5 后续待办

- [ ] 确定哪些历史文档需要存档（用户自行梳理）
- [ ] Markdown ↔ Word 无损转换方案（依赖模板确定）
- [ ] 历史文档批量迁移（依赖试点验证）

### 2.6 关键决策点

**Q1：格式转换方案？**
- Markdown → Word：Pandoc + 自定义 Word 模板（reference-doc）
- Word → Markdown：Pandoc（基础）或 Mammoth.js（保留结构）
- 组网图处理：Draw.io（复杂）/ Mermaid（简单）单独方案

**Q2：Obsidian 是否能承载？**
- 需验证：100+ 文档、双向链接、AI 集成、团队协作（如有）
- 建议：搜索 Obsidian 知识库案例，看是否有类似规模的成功实践
- 进展：架构讨论预计很快出结果

**Q3：组网图通用格式？**
- 候选方案：
  - Mermaid（Markdown 原生，表达能力有限）
  - Draw.io（通用，可导出图片，内外网通用）
  - PlantUML / D2（代码即图，版本控制友好）

### 3.1 需求痛点

| 痛点 | 说明 | 严重程度 |
|-----|------|---------|
| 账务管理不细致 | 账目未完全梳理，存放位置缺乏科学分类 | 🟡 中 |

| 特殊物料丢失风险 | 未做标记或存放位置不明，清理时被混放甚至丢失 | 🔴 高 |
| 积压物料待处理 | 存量物料急需清理，但未投入足够时间 | 🟡 中 |
