## 一、项目管理系统

### 1.1 需求痛点

- **核心痛点**：人力排布依赖人工，效率低且缺乏显性化模型支撑
- 部门现有管理系统虽有人力模型定义，但未显性化，大家未聚焦于此
- 需要将"项目管理系统"封装为 skill，扩展到整个模块使用

### 1.2 关键要做的事情

| 关键事项 | 说明 | 关键点 |
|---------|------|-------|
| **人力能力模型简化** | 融合两份输入参考，产出简化版模型 | 聚焦两个核心维度：出差能力 + 项目复杂度适配 |
| **WeLink CLI 调研** | 研究自动信息接收的实现路径 | WeLink 可能不支持机器人模式，需寻找替代方案 |

### 1.3 约束与输入

| 约束项 | 内容 |
|-------|------|
| 输入参考 A | GitHub Hermes 梳理的人力能力模型（外网） |
| 输入参考 B | 部门现有系统的人力模型定义（内网，需用户自行查找） |
| WeLink 文档 | 已有文档，但需内网搜索他人实践案例 |
| 数据录入优化 | 非当前最高优先级，节后处理 |

### 1.4 五一任务清单

| 任务 | 类型 | 预计时长 | 交付物 |
|-----|------|---------|-------|
| 整合人力能力模型 | 执行 | 3-4h | `人力能力模型-v2.md` |
| WeLink 集成调研 | 调研 | 2h | `WeLink集成调研.md` |

### 1.5 后续待办

- [ ] 从内网查找部门现有系统的人力模型定义
- [ ] 数据录入意图理解优化（节后）

## 二、知识库管理（TSE 测试工作集）

### 2.1 需求痛点

- **核心痛点**：约 100 份历史文档处于混乱状态，格式不统一（文档 + Excel），无结构化管理
- 测试用例、测试数据、测试指导三者缺乏关联
- Markdown ↔ Word 转换存在格式失真问题
- 组网图无法在 Markdown 中直接呈现，也无法从 Word 还原

### 2.2 关键要做的事情

| 关键事项 | 说明 | 关键点 |
|---------|------|-------|
| **底层架构选型** | 确定知识库承载方案 | 🔴 阻塞后续所有任务，五一必须确定 |
| **文件结构设计** | 定义工作区目录结构 + AI 引导说明 | 基于分类维度：运营商 / 年份 / 项目 |
| **用例模板制定** | 制定 Markdown 格式 + 双向链接规范 | 模板确定后才能批量迁移 |
| **组网图方案** | 寻找通用标准格式，内外网通用 | 需调研 Mermaid / Draw.io / 其他方案 |

### 2.3 约束与输入

| 约束项 | 内容 |
|-------|------|
| 底层架构倾向 | Obsidian 承载，但未找到类似完整方案参考 |
| 组网图现状 | PPT 形状 / 公司内 Visio 类软件 |
| 组网图目标 | 通用标准形式，内外网通用 |
| 历史文档分类维度 | 运营商 → 年份 → 项目 |
| 单项目内容结构 | 最终版规范 + 过程稿 + 数据结果（预测 + 测试） + 组网/配置条件 |
| 存档范围 | 尚未完全确定，需用户自行梳理 |
| 公司系统 | 有系统但无法精细化管理 |

### 2.4 五一任务清单

| 任务 | 类型 | 预计时长 | 交付物 |
|-----|------|---------|-------|
| Obsidian 架构调研 | 调研 | 2-3h | 调研结论（是否可行 + 参考案例） |
| 文件结构设计 | 设计 | 2h | 目录结构方案 |
| 用例 Markdown 模板制定 | 设计 | 2h | 模板文件 |
| 组网图方案调研 | 调研 | 2h | 方案建议（Mermaid / Draw.io / 其他） |
| 用例 Markdown 化试点 | 执行 | 3h | 5-10 份试点文档 |

### 2.5 后续待办

- [ ] 确定哪些历史文档需要存档（用户自行梳理）
- [ ] Markdown ↔ Word 无损转换方案（依赖模板确定）
- [ ] 历史文档批量迁移（依赖试点验证）

### 2.6 关键决策点

**Q1：Obsidian 是否能承载？**
- 需验证：100+ 文档、双向链接、AI 集成、团队协作（如有）
- 建议：搜索 Obsidian 知识库案例，看是否有类似规模的成功实践

**Q2：组网图通用格式？**
- 候选方案：
  - Mermaid（Markdown 原生，表达能力有限）
  - Draw.io（通用，可导出图片，内外网通用）
  - PlantUML / D2（代码即图，版本控制友好）

## 三、实验室物料管理

### 3.1 需求痛点

| 痛点 | 说明 | 严重程度 |
|-----|------|---------|
| 账务管理不细致 | 账目未完全梳理，存放位置缺乏科学分类 | 🟡 中 |
| 管理难度大 | 项目多、物料种类繁杂，负责人对部分物料缺乏认知 | 🟡 中 |
| 特殊物料丢失风险 | 未做标记或存放位置不明，清理时被混放甚至丢失 | 🔴 高 |
| 积压物料待处理 | 存量物料急需清理，但未投入足够时间 | 🟡 中 |
| 存放空间不足 | 已有方案：撤悍马桌 + 隔音舱，改造为货架 | 🟡 中 |
| 周转效率与成本 | 周转频率高，需实时跟踪 + 减少人工投入 | 🟡 中 |

### 3.2 关键要做的事情

| 关键事项 | 说明 | 关键点 |
|---------|------|-------|
| **全生命周期流程设计** | 定义四环节流程 + 表单模板 | 申购建账 → 物品管理 → 标准周转 → 健康审视 |
| **管理对象分类** | 区分研发物料 vs 资产 | 公司有标准区分，方案需沿用 |
| **方案文档产出** | 可落地的详细计划 | 五一核心交付物 |

### 3.3 约束与输入

| 约束项 | 内容 |
|-------|------|
| 公司系统 | 有现成系统，但无法精细化管理到组内详细物料 |
| 研发物料 vs 资产 | 公司有标准区分和管理模式 |
| 空间改造 | 协调他人执行，方案文档中提供建议即可 |
| 五一目标 | 产出方案文档，不涉及执行 |

### 3.4 五一任务清单

| 任务 | 类型 | 预计时长 | 交付物 |
|-----|------|---------|-------|
| 方案文档起草 | 执行 | 3h | `实验室物料管理方案.md` |
| 全生命周期流程设计 | 设计 | 2h | 流程图 + 表单模板建议 |

### 3.5 方案文档结构

```markdown

## 一、问题现状（6 大痛点）
## 二、管理对象分类（研发物料 / 资产）

    - 物品管理（分类/存放/查找）
    - 标准化周转
```
